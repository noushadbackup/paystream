How a payment moves

From the tap to the ledger in five steps

Ingest

Kafka + Avro

Payment events and ledger changes (Debezium CDC) under schema contracts with backward compatibility.

Stream

Flink, exactly-once

Dedup of app retries, event-time windows, four built-in detectors and analyst rules loaded without a deploy.

Decide

Decision API

The gateway asks before authorising. One Redis read of Flink's features, limits, flags and a LightGBM score.

Act

Cases

Alerts become cases with SLAs. A verdict freezes the account or clears it, and becomes a training label.

Store

Iceberg + dbt

Bronze, silver and gold; AML reports on the Dhaka business day; stream reconciled to the ledger.

The allocator decided the last ten minutes

The first hour held p95 under 300 ms for 48 minutes, then checkpoints went from 1 s to 25 s and the job fell behind. The TaskManager had grown to 8.1 GB against a 6.5 GB budget: glibc malloc fragments RocksDB's native memory. With jemalloc, the same hour stayed at about 4.5 GB, with checkpoints under 1.8 s throughout.

RocksDB was starving, not the CPU

With the default config the payments job got 686 MB of RocksDB memory shared by ten keyed operators. Memtables stayed tiny, a single compaction thread fell behind and writes stalled. Four background threads, dynamic level sizing, heap timers and a memory budget that gives the payments job about 1,640 MB took it from falling behind to holding the rate.

What the benchmark caught

Every run found something the unit tests could not

Each run replays generated traffic with labelled fraud through the real job graph, then scores every alert against the labels. These are the runs in the order they happened, and what each one changed.

State layout decided throughput

On RocksDB every state access is a serialised lookup. The online-features operator kept four separate states per account and dominated the job. Collapsing them into one value per account, with the same output contract, raised throughput by 61% on the same data.

Before3,560 ev/s
After5,743 ev/s

The simulator was the bug

Precision was 2%: 5,483 velocity alerts, mostly from one simulated customer who made 9,842 payments in 53 minutes. An uncapped Pareto draw over millions of users does that; no real wallet does. User activity is now capped at 20 times the mean, with a test that no account dominates.

A fresh deployment is blind to takeovers

The new-device rule needs 90 days of which phone each account uses. From empty state it caught no account takeovers at all. Of the 11 still missed, 9 had no payment in the two hours of history the benchmark used. A State Processor API job now builds that history from the lakehouse into a savepoint the payments job starts from.

Four sigma is not rare at 20,000 agents

The agent cash-out spike rule used mean plus four standard deviations. Tested on every agent on every cash-out, that raised about 160 false alerts an hour. It now uses the exact Poisson tail at one in a million against each agent's own hourly rate.

Out-of-order events hid structuring

Three agents' cash-ins into one wallet come through different Kafka partitions with different lag. When the middle one arrived last, the analyst rule never re-checked the window that now held all three. Each arrival is now checked against every window it falls in, in Flink and in the Python backtester, pinned by a shared conformance test.

One threshold does not fit every account

On the desktop run's traffic, 1 million accounts at 2,000 payments a second, the busiest legitimate accounts send two or three transfers a minute, so a fixed bar of six a minute raised 2,696 false velocity alerts. The rule now compares each account with its own rate, a Gamma-Poisson baseline that alerts below a one-in-100,000 tail, and learns those rates from the lakehouse into the savepoint before it starts. Every velocity burst and takeover is still caught.

What these numbers are not

Limits of the measurements

  • Everything ran on one 4-vCPU container: the replay reads a file to find the Flink job's ceiling, and the live runs share the box between Kafka, Flink, Redis and the generator, so 2,000 payments/s is a rate it sustains with headroom, not a cluster's limit. One broker: the desktop chaos run killed it and the job recovered exactly, but with a single broker that is a restart, not a failover between replicas.
  • Traffic and fraud are simulated, with labels from the simulator. Precision is account-level: an alert counts when its account has labelled fraud. The 72.5% on 1 million accounts is a replay; the desktop stack run itself does not load the rate history yet.
  • Two hours of bootstrapped history stand in for the 90 days production would read, so takeover recall here is a floor.
  • The Kubernetes and Terraform setup is validated in CI (schemas, lint, terraform validate) and has not yet been applied to a real AWS account.
